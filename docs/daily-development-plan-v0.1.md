## 术语表与命名约定

| 规范名称 | English / Acronym | 在本计划中的职责边界 | 不代表什么 |
| --- | --- | --- | --- |
| 工作日 | Workday | 一名开发者投入 6–7 小时有效开发时间的一个工作日 | 不代表自然日或全天连续工作 |
| 日计划项 | Daily Item | 当天必须完成并验证的一项可观察结果 | 不代表可以跳过测试的任务标题 |
| 阶段检查点 | Stage Checkpoint | 阶段末构建、测试、覆盖率和运行验收的集合 | 不代表仅提交代码 |
| 个人可用版 | Personal Usable Release | 阶段 0–3C 完成后，可在个人控制的可信网络中使用的版本 | 不代表公网生产版或多租户服务 |
| 缓冲日 | Recovery Buffer | 用于处理返工、工具链、平台差异和故障复现的预留工作日 | 不代表预先承诺一定会消耗 |

## 1. 估算边界

本计划把“个人可用版”定义为阶段 0、1A–1F、2A–2B、3A–3C。完成后应支持：

- 单节点可恢复日志、主键索引、快照和 KV 操作。
- 单分区事务、`CAS`、批量写入、超时和资源上限。
- Edge Node 到 Sync Hub 的单向、至少一次同步。
- 幂等去重、连续游标、断点续传、重试、乱序处理和坏事件隔离。
- 本机 Docker 双节点弱网验收和可重复的 CLI 运行入口。

本版本明确不包含双向同步、多分区并行、TLS/身份认证、备份运维、SDK、有限查询层、公网部署和多租户隔离。因此它适合个人实验、家庭网络或受控局域网，不应直接暴露到公网。

工作日编号从第一个正式开发日开始，不预设日历日期。每个工作日必须同时完成“实现或设计输出”和“当日验证”；未通过的日计划项顺延，不能用下一日的新代码掩盖失败。

## 2. 每日固定节奏

每天按以下顺序执行：

1. 阅读前一日失败记录和未完成项，确认当天输入没有漂移。
2. 完成当天限定范围的代码、测试辅助代码或协议文档。
3. 运行该日验证命令，至少包括相关单元测试、`cargo fmt --all -- --check` 和源码规模检查。
4. 更新验证记录，写明输入、输出、失败原因、未完成项和下一日依赖。
5. 阶段检查点额外运行 workspace Clippy、workspace 测试、关键模块覆盖率和适用的故障/ Docker 测试；通过后才提交并推送。

## 5. 日计划的调整规则

- 单日偏差不超过 1 天：在下一日吸收，不改变阶段检查点。
- 连续两日无法通过同一验收：暂停新增功能，第三日只做故障复现、设计修正和测试补齐。
- 阶段检查点延期 3 天以内：使用后续缓冲日，不压缩覆盖率、恢复或 Docker 验收。
- 阶段检查点延期超过 3 天：重新估算剩余阶段，并记录容量、文件格式、恢复语义或环境变化原因。
- 关键模块覆盖率低于 100%、文件超过 600 行、函数超过 120 行、工作树有无关修改或 Docker 不可用时，当前阶段保持未完成。

阶段 4–6C 不计入上述 100 个工作日个人版倒计时。基于个人每天 6–7 小时有效开发时间，扩展能力还需要约 60–85 个工作日：
