## 术语表与命名约定

| 规范名称 | English / Acronym | 在本项目中的职责边界 | 不代表什么 |
| --- | --- | --- | --- |
| 通用内核 | Generic Core | 负责记录存储、本地事务、变更日志、同步和恢复 | 不包含任何行业业务规则 |
| 边缘节点 | Edge Node | 在弱网或断网期间继续本地读写的节点 | 不代表网络连接本身 |
| 同步中心 | Sync Hub | 接收、保存、应用和分发变更的节点 | 不默认等同于 Raft Leader 或全局唯一写入者 |
| 分区 | Partition | 保证局部顺序和事务边界的最小写入单元 | 不代表一个独立数据库产品 |
| 变更事件 | Change Event | 描述一次已提交数据变化、可重试且可幂等应用的记录 | 不代表临时网络消息 |
| 变更日志 | Change Log | 持久保存变更事件并提供同步游标的日志 | 不只是运行日志 |
| 当前状态 | Current State | 根据已应用变更维护的最新记录视图 | 不替代变更日志 |
| 写入归属 | Write Ownership | 指定某个业务对象或分区的主要写入节点 | 不代表永久不可迁移 |
| 同步游标 | Sync Cursor | 记录某个来源或分区已经发送、接收或应用的位置 | 不使用物理时间戳代替序列位置 |
| 冲突记录 | Conflict Record | 保存无法按当前规则自动应用的变化及其来源 | 不静默覆盖旧值 |

后续正文、接口字段、表名和架构图统一使用以上规范名称。具体行业名称属于数据集和同步配置，不进入通用内核的固定概念。

## 1. 产品定义

Lattice DB 是一个从零实现的、写入优先、分区化、本地优先的通用边缘分布式数据库。所有节点运行同一套数据库内核，只通过配置区分边缘节点和同步中心。

第一版的目标是解决多个节点在长时间断网、低带宽、高延迟、丢包、重复发送和连接反复建立时的数据保存与同步问题。后续通过通用数据模型和同步配置扩展到不同的行业和设备环境。

“从零实现”表示不把 SQLite、Redis、MySQL、PostgreSQL、MongoDB、消息队列或现成分布式数据库作为运行时依赖。允许使用操作系统文件系统、网络、线程、TLS、加密和压缩等标准能力或底层库，但存储引擎、事务管理、变更日志、同步协议、冲突处理和分区机制由本项目实现。

## 2. 参考数据库的取舍

| 参考对象 | 借鉴内容 | 首期不直接实现的内容 |
| --- | --- | --- |
| SQLite | WAL 思路、事务恢复、单机嵌入式部署 | 不嵌入 SQLite 作为存储引擎 |
| Redis | 简单命令、批量操作、TTL、原子操作 | 不把内存数据结构作为主存储 |
| MySQL | 表、约束、索引和事务边界 | 不追求 MySQL 协议或 SQL 兼容 |
| PostgreSQL | MVCC、类型、可靠性和分区思想 | 不依赖 PostgreSQL 作为中心存储 |
| MongoDB | 文档和 JSON 字段 | 不首期实现完整 MongoDB 查询模型 |

## 3. 目标场景

### 3.1 弱网边缘场景

- 边缘节点持续产生设备、位置、业务和审计事件。
- 边缘节点在断网期间继续写入，数据不能依赖同步中心在线。
- 同步中心接收多个边缘节点的批量变更，同时产生配置、任务和控制指令。
- 链路可能有高延迟、丢包、乱序、重复请求、带宽波动和较长离线时间。
- 边缘节点和同步中心都属于写多读少，读取主要是按主键、业务对象或时间范围查询。

### 3.2 通用配置能力

通用内核还应支持以下配置，而不修改核心代码：

- 节点和数据集的写入归属。
- 数据同步方向。
- 分区键和分区数量。
- 事件优先级、保留期限和带宽预算。
- 冲突策略和人工解决方式。
- 节点离线、重连、快照恢复和日志清理规则。

## 4. 一致性边界

首期采用以下一致性语义：

- 单分区本地事务满足 ACID。
- 一个事务中的业务记录和变更事件必须一起提交或一起回滚。
- 同步采用至少一次传输，目标节点通过幂等键保证重复应用不会重复产生效果。
- 节点之间采用最终一致，不承诺断网期间的全局强一致。
- 单分区内可以保证提交序列；不同分区之间不提供全局顺序。
- 跨节点和跨分区事务不在首期范围内。
- 本地提交成功不等于同步中心已经接收或应用。

调用方可以观察以下状态：

```text
local_committed  本地日志已经持久化并提交
hub_received     同步中心已经持久化接收到的变更
hub_applied      同步中心已经将变更应用到当前状态
```

## 5. 数据模型

### 5.1 首期数据模型

首期采用键值和文档式模型，不实现完整 SQL。核心操作包括：

- `PUT`：写入完整值。
- `PATCH`：按字段修改文档值。
- `GET`：按主键读取。
- `DELETE`：写入删除标记。
- `CAS`：按版本号条件更新。
- `BATCH`：在同一分区内提交多个操作。
- `SCAN`：按分区、主键范围或时间范围读取。

值类型支持整数、浮点数、布尔、字符串、字节数组和 JSON 文档。后续可以在此模型上增加受限 SQL 查询层，但查询语法不能反过来决定同步协议和日志格式。

### 5.2 记录元数据

每条可同步记录至少包含：

```text
dataset_id
partition_id
record_id
version
origin_node_id
origin_sequence
created_at
updated_at
deleted_at
payload
```

`created_at` 和 `updated_at` 仅用于查询和展示，不用于判断跨节点的先后顺序。顺序由来源节点序列、分区序列和事务提交位置决定。

### 5.3 追加事件与当前状态

事件数据优先采用追加写入，例如设备采集、日志和状态变化。需要查询最新状态时，由数据库根据已应用事件维护当前状态。

当前状态可以更新，但必须保留版本和来源信息。旧事件不能因为当前状态已经存在而直接丢弃，直到所有需要该事件的节点都完成确认并且保留策略允许清理。

## 6. 自研存储引擎需求

### 6.1 日志和文件格式

- 使用追加式日志段保存事务记录和变更事件。
- 日志记录包含长度、类型、序列、校验和和负载。
- 事务至少包含开始、操作和提交标记。
- 未发现提交标记的事务在恢复时全部丢弃。
- 文件格式包含版本号，禁止无提示地读取不兼容格式。
- 日志损坏时停止传播损坏记录，并进入修复或隔离状态。

### 6.2 当前状态索引

- 首期只实现主键索引和必要的分区索引。
- 索引更新必须与事务提交保持一致。
- 索引不能成为所有写入的全局锁。
- 后续可以增加异步查询状态表和时间索引。

### 6.3 快照和压缩

- 支持按分区创建快照。
- 快照记录覆盖的日志位置。
- 恢复后从快照位置之后继续读取增量日志。
- 未同步、未确认或仍可能被离线节点读取的日志不能提前删除。
- tombstone 必须保留到删除安全窗口结束。

## 7. 事务需求

首期选择单分区、单写入队列的事务模型：

- 同一分区内的写入按提交顺序执行。
- 事务成功后才推进分区提交序列。
- 事务失败时业务记录、当前状态和变更日志全部回滚。
- 读取使用一个确定的提交序列快照。
- `CAS` 用于离线重连后的版本检查。
- 长事务必须有超时和资源上限。
- 跨分区事务先返回不支持，而不是隐式拆分。

## 8. 同步协议需求

同步协议与具体传输方式分离。首期可以使用可靠的双向字节流，后续再接入 HTTP、QUIC 或其他链路，不改变同步语义。

### 8.1 握手信息

双方握手至少交换：

- 节点 ID。
- 协议版本和文件格式版本。
- 数据集和分区版本。
- 已发送、已接收和已应用的同步游标。
- 快照能力和压缩能力。
- 带宽预算和批量大小限制。

### 8.2 变更事件

```text
operation_id
transaction_id
origin_node_id
origin_sequence
partition_id
record_id
operation_type
base_version
payload
schema_version
checksum
```

### 8.3 弱网行为

- 支持批量上传和批量下载。
- 支持超时、指数退避和随机抖动。
- 支持断点续传，不依赖单次连接完成同步。
- 重复请求不能重复产生业务效果。
- 乱序事件暂存或拒绝应用，不得错误推进游标。
- 单条坏事件进入隔离队列，不阻塞其他分区。
- 支持高优先级事件抢占普通事件。
- 待同步日志超过容量上限时必须限流、拒绝低优先级写入或触发报警。

## 9. 同步配置

不同应用场景通过数据集配置表达，不修改通用内核：

```text
dataset_id
partition_key
write_owner: edge | hub | shared
sync_direction: edge_to_hub | hub_to_edge | bidirectional
delivery: at_least_once
conflict_policy: reject | custom
priority
retention
```

推荐默认规则：

- 边缘产生的事件：`edge_to_hub`，追加写入。
- 同步中心产生的任务和配置：`hub_to_edge`，带命令状态。
- 双方修改的业务对象：`shared`，必须版本检查和冲突记录。
- 高优先级数据优先同步，普通日志允许延迟和压缩。

## 10. 冲突处理

首期优先减少冲突，不追求自动合并：

- 同一业务对象尽量固定一个主要写入节点。
- 非主要写入节点提交修改时使用版本条件。
- 版本不匹配时创建冲突记录。
- 冲突记录保存旧值、新值、来源节点、事务 ID 和操作序列。
- 冲突解决结果也必须成为新的可同步操作。
- 默认禁止静默使用最后写入者覆盖。
- 字段级合并、逻辑时钟和 CRDT 放到后续阶段。

## 11. 运行角色和分区

所有节点运行同一个引擎，角色只影响配置和默认策略：

- `standalone`：单节点开发和测试。
- `edge`：允许断网本地提交并保存待同步日志。
- `hub`：接收多个来源、并行处理多个分区，并产生下行变更。

首期采用静态分区配置，不实现自动分片和自动选主。分区迁移必须先建立快照边界，再切换写入归属，防止同一对象同时被两个分区写入。

## 12. 非功能需求

### 可靠性

- 已确认的本地提交在进程崩溃和机器重启后可恢复。
- 已确认的同步中心接收不会因为重复重试而重复应用。
- 快照、日志和当前状态可以互相校验。
- 提供备份、恢复和损坏隔离命令。

### 可观测性

至少记录：

- 写入吞吐、批次大小和提交延迟。
- 每个分区的日志增长和热点程度。
- 待发送、待接收和待应用的事件数量。
- 最旧未同步事件的年龄。
- 重试、去重、冲突和隔离事件数量。
- 快照、恢复和压缩耗时。
- 数据文件、日志文件和可用磁盘空间。

### 安全性

生产部署需要：

- 节点身份认证。
- 链路加密。
- 数据集和操作权限。
- 防止旧操作重放。
- 敏感数据不写入普通日志。

## 13. 明确不在首期范围内

- 完整 MySQL 或 PostgreSQL SQL 兼容。
- 完整 MongoDB 查询 API。
- Redis 全部数据结构、脚本和发布订阅能力。
- 跨分区或跨节点强一致事务。
- 任意多主自动合并。
- 自动选主、自动分片和全球多中心复制。
- 复杂 JOIN、查询优化器和分析型执行引擎。

## 14. 分阶段实现和验收

本节只保留能力范围和阶段关系，便于维护需求基线。每个阶段的开发切片、前置条件、测试证据、量化阈值和停止规则见[后续开发计划](development-plan-v0.1.md)。

需求阶段与开发计划的对应关系如下：

| 需求阶段 | 开发计划范围 | 说明 |
| --- | --- | --- |
| 阶段 0：需求和协议冻结 | 阶段 0 | 冻结实现语言、文件格式、确认语义、游标规则、容量参数和故障矩阵后才能写持久化代码 |
| 阶段 1：单节点存储引擎 | 阶段 1A–1F | 先交付日志帧和最小恢复，再逐步增加索引、快照、KV API、压缩和安全清理 |
| 阶段 2：单分区事务 | 阶段 2A–2B | 在 KV API 之上提供事务、提交序列、快照读取、`CAS` 和资源上限 |
| 阶段 3：双节点弱网同步 | 阶段 3A–3C | 明确区分 `hub_received` 与 `hub_applied`，并以本机 Docker 完成多节点验证 |
| 阶段 4：双向数据同步 | 阶段 4 | 先支持单分区双向同步、操作状态和 `reject + conflict record`，自动合并仍不在首期 |
| 阶段 5：多分区和中心并行写入 | 阶段 5 | 用独立分区队列、热点限流和可测阈值验证并行能力 |

## 15. 需要在开发前冻结的参数

1. 单个边缘节点平均和峰值写入量。
2. 同步中心合计峰值写入量。
3. 单条记录平均大小和每日数据量。
4. 最大离线时间和日志保留时间。
5. 数据主要是追加事件，还是反复更新同一对象。
6. 是否允许多个节点修改同一对象。
7. 是否需要删除传播和历史版本查询。
8. 首期目标操作系统和实现语言。

在这些参数冻结之前，不应实现完整 SQL、自动分片或跨节点事务。首个可交付目标应是：自研日志、单分区事务、可恢复同步和弱网故障测试。
