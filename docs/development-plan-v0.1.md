## 术语表与命名约定

| 规范名称 | English / Acronym | 在本计划中的职责边界 | 不代表什么 |
| --- | --- | --- | --- |
| 阶段 | Stage | 一组有共同前置条件和验收目标的交付范围 | 不代表一次提交或一次发布 |
| 开发切片 | Development Slice | 阶段内可以独立实现、验证和提交的最小功能范围 | 不代表随意拆分的任务列表 |
| 完成定义 | Definition of Done / DoD | 判断一个切片能否交付的证据集合 | 不代表“代码已经可以运行” |
| 故障测试矩阵 | Fault Test Matrix | 记录注入点、预期状态和核验结果的测试集合 | 不代表生产监控告警 |
| 连续游标 | Contiguous Cursor | 只推进到已经连续确认的来源节点和分区序列位置 | 不代表最新收到的最大序列 |
| 接收确认 | Received ACK | 表示变更及去重记录已经持久化 | 不表示当前状态已经应用 |
| 应用确认 | Applied ACK | 表示当前状态和应用游标已经持久化 | 不表示其他节点已经收到 |

后续正文统一使用以上规范名称。需求文档定义一致性边界；本计划只定义实现顺序、交付边界和验证证据，不重新定义业务语义。两份文档发生冲突时，以需求基线中的已冻结约束为准，并在下一版文档中记录修订原因。

## 1. 计划原则

1. 先冻结影响文件格式和同步语义的参数，再编写持久化代码。
2. 每个开发切片只覆盖一个可验收行为，完成验证后单独提交并立即推送当前工作分支；未特别指定时直接在 `main` 分支开发。
3. 单元测试和属性测试验证局部规则；跨进程、网络故障和容器部署才使用集成测试证明系统行为。
4. 集成测试只使用本机 Docker。验证记录必须包含服务、镜像版本、端口、启动时间、清理结果和未完成项；Docker 不可用时，集成验收保持未完成。
5. 未支持的跨分区事务、自动选主、自动分片和静默冲突覆盖必须返回明确错误或生成明确记录，不能隐式降级。
6. 量化目标没有冻结前，只能完成协议和测试设计，不能宣称性能或容量达标。

## 2. 阶段 0：开发前冻结

### 2.1 必须冻结的决策

阶段 0 的出口不是“文档写完”，而是所有影响文件格式、恢复结果和测试负载的决策都有版本化记录。至少需要冻结以下内容：

| 决策项 | 最低冻结内容 | 未冻结时的阻塞范围 |
| --- | --- | --- |
| 实现语言和目标系统 | 语言版本、编译目标、支持的 Windows/Linux 版本 | 阻塞代码仓库、构建和 CI |
| 持久化确认 | `local_committed` 的写入、刷盘和提交标记顺序 | 阻塞崩溃恢复和 ACK 语义 |
| 标识符 | 节点、数据集、分区、记录、事务和操作 ID 的格式及生成方式 | 阻塞日志、去重和冲突记录 |
| 序列分配 | 来源节点与分区序列的分配时机、空洞和重启恢复规则 | 阻塞连续游标和乱序处理 |
| 编码格式 | 字节序、整数宽度、字符串编码、长度上限和校验算法 | 阻塞文件兼容性 |
| 容量边界 | 最大记录、事务、批次、日志段、快照和待同步队列大小 | 阻塞磁盘满和限流测试 |
| 错误行为 | 截断、校验和错误、版本不兼容、磁盘满时的停止、隔离或拒绝方式 | 阻塞恢复验收 |
| 文件布局 | 数据目录、日志目录、快照目录、临时文件和锁文件命名 | 阻塞备份、清理和故障注入 |
| 同步确认 | `hub_received`、`hub_applied` 的推进条件，游标持久化位置和重启恢复 | 阻塞同步协议实现 |
| 性能目标 | 吞吐、p95 提交延迟、恢复时间、同步滞后、磁盘占用和重试上限 | 阻塞性能验收 |

需求基线第 15 节中的八项输入参数是上述决策的业务来源，但不能替代这些工程参数。每项决策都要注明数值、单位、测量方法、适用版本和变更影响。

### 2.2 阶段 0 交付物和验收

交付物：

- 参数冻结记录和变更规则。
- 记录帧、事务记录、变更事件和错误码的版本草案。
- `local_committed -> hub_received -> hub_applied` 状态图，以及 ACK、游标和重启后的推进规则。
- 故障测试矩阵和最小测试数据生成规则。
- 开发仓库目录、测试入口、验证记录目录和本机 Docker 测试约定。

验收条件：

- 每个状态转换都有触发条件、持久化边界、失败结果和可观察字段。
- 能够对提交前崩溃、提交标记损坏、日志截断、校验和错误、版本不兼容、磁盘不足、重复事件和游标缺口给出唯一预期结果。
- 所有后续阶段都有明确前置阶段；未冻结项被登记为阻塞项，不以默认值隐藏。

## 3. 阶段路线和交付边界

| 阶段 | 范围边界 | 必要前置 | 主要验收证据 |
| --- | --- | --- | --- |
| 0 | 规范、参数、状态机和测试基线冻结 | 需求基线 | 冻结记录、协议草案、故障矩阵、测试入口 |
| 1A | 日志记录帧、长度/类型/序列/校验和、文件版本检查 | 阶段 0 | 合法帧可读，坏帧和不兼容版本有确定错误 |
| 1B | 最小提交标记和崩溃恢复，不提供完整事务 API | 1A | 已提交记录可恢复，未提交记录不可见，截断不会伪造提交 |
| 1C | 单分区主键索引和索引恢复 | 1B | 索引与已提交日志一致，重建结果可核验 |
| 1D | 分区快照和增量恢复 | 1C | 快照边界可恢复，恢复后从边界继续读取日志 |
| 1E | 最小 `PUT/GET/DELETE/SCAN` KV API | 1C | API 结果与当前状态、日志和版本一致 |
| 1F | 压缩和安全清理 | 1D、阶段 0 保留规则 | 未确认日志和 tombstone 不被提前清理，清理后仍可恢复 |
| 2A | 单分区事务、提交序列和批量写入 | 1E | 原子提交、回滚、批次边界和提交序列通过属性测试 |
| 2B | 快照读取、`CAS`、超时和资源上限 | 2A | 并发读写、版本失败和超限行为稳定 |
| 3A | 单分区、单向双节点握手、事件发送和连续游标 | 2B、1D | ACK 只在对应持久化条件满足后推进，缺口不越过 |
| 3B | 重试、幂等、断点续传、乱序暂存或拒绝和坏事件隔离 | 3A | 断网、重连、重复、乱序和坏事件测试通过 |
| 3C | 本机 Docker 双节点弱网集成验证 | 3B | 记录镜像、端口、故障注入、启动和清理结果 |
| 4 | 单分区双向同步、优先级、带宽预算、冲突记录和操作状态 | 3C、冲突规则 | 下行命令可追踪，版本冲突生成可同步记录，高优先级等待时间可测 |
| 5 | 静态多分区路由、独立写入队列、热点限流和分区快照 | 4 | 分区隔离、中心重启和热点负载测试通过 |
| 6A | 身份认证、链路加密、权限和重放防护 | 5 | 未授权、旧操作和敏感日志测试通过 |
| 6B | 备份、恢复、损坏隔离、容量告警和指标 | 5 | 备份恢复、损坏处理和指标结果可核验 |
| 6C | SDK、数据集配置和有限查询层 | 6A、6B | 新数据集和拓扑只改配置或 SDK 调用，不改内核 |

阶段 1 拆分后，只有 1A 和 1B 完成，才能讨论“已提交事务可以恢复”；1D、1E 和 1F 都在 1C 后形成独立切片，1F 不得成为 2A 的隐式前置；阶段 2 才对外提供完整事务 API。阶段 3 的“收到”与“应用”保持分离，不能用收到最大序列替代连续游标。

## 4. 首个可执行开发切片

计划批准后，按以下顺序开始实现；每个切片单独验收，不能跨切片提前承诺后续能力。

### Slice 0A：协议和故障基线

- 输入：需求基线和阶段 0 冻结清单。
- 输出：版本化的记录字段、错误码、状态转换、游标规则和故障矩阵。
- 测试：测试数据生成规则、状态转换表和边界值检查；此切片不要求运行数据库代码。
- 退出条件：所有未决项都有负责人和阻塞说明，且不会由实现者临时决定。

### Slice 0B：仓库和验证入口

- 输入：Slice 0A 的语言、目标系统和目录布局决策。
- 输出：最小可构建仓库、库/API 边界、测试辅助代码、命令行或测试入口、验证记录模板。
- 测试：空数据集启动、构建、单元测试、格式检查和静态检查。
- 退出条件：新开发者能够按 README 在本机完成构建和测试；失败时能区分环境问题与代码问题。

### Slice 1A：日志记录帧

- 输入：编码、容量和错误行为决策。
- 输出：追加日志段、记录帧编码/解码、文件版本检查和校验和验证。
- 测试：合法帧、空负载、最大负载、长度溢出、截断、坏校验和、未知版本和段轮换。
- 退出条件：测试能证明解码器不会读取记录边界之外的数据，错误不会被当成空记录继续传播。

### Slice 1B：最小提交恢复

- 输入：Slice 1A 和提交标记规则。
- 输出：开始/操作/提交记录的最小恢复器，以及提交前后崩溃注入点。
- 测试：写入前、操作记录后、提交标记前、提交标记后和重启恢复；核验当前状态、日志长度和提交序列。
- 退出条件：已提交记录可重复恢复，未提交记录不可见，恢复结果不依赖临时内存状态。

## 5. 跨阶段完成定义

每个开发切片必须同时交付以下证据：

1. 实现代码、接口或格式文档，以及必要的测试辅助代码。
2. 自动化测试结果：单元测试、属性测试、崩溃恢复测试或本阶段适用的组合。
3. 故障测试记录：注入点、输入、预期结果、实际结果和失败日志。
4. 性能或容量结果：使用已冻结的测试数据、单位、环境和阈值；没有阈值时标记为未完成。
5. 未完成项和已知限制：明确不在当前切片中的能力，不用 TODO 掩盖验收缺口。
6. 版本控制记录：一个可验收切片对应一个 Conventional Commit；验证通过后立即推送当前工作分支。若用户明确指定功能分支，合并到 `main` 并重新验证后删除已合并分支。

任何一项证据缺失、测试失败、Docker 集成环境不可用或工作树混入无关修改，都不能将该切片标记为完成。

## 6. 故障测试矩阵

| 类别 | 注入点或输入 | 必须核验的结果 |
| --- | --- | --- |
| 进程崩溃 | 写入前、日志记录后、提交标记前后、索引更新前后、ACK 前后 | 已提交/未提交可见性、日志边界、索引、状态和游标一致 |
| 存储损坏 | 截断、长度异常、校验和错误、未知版本、快照损坏 | 停止或隔离位置、错误类型、是否允许继续读取其他分区 |
| 容量耗尽 | 日志段、快照、待同步队列和磁盘剩余空间达到上限 | 限流、拒绝、报警和恢复后的继续写入规则 |
| 网络异常 | 断网、重连、延迟、丢包、重复、乱序、半包和坏包 | 重试上限、幂等结果、缺口处理、连续游标和隔离队列 |
| 数据语义 | 重复 `operation_id`、重复事务、CAS 失败、冲突解决重复提交 | 业务效果只产生一次，失败和冲突记录可追踪 |
| 重启恢复 | 边缘节点、同步中心和双端同时重启 | 日志位置、去重记录、收到/应用状态和游标恢复 |

阶段 3 及以后需要至少运行一次本机 Docker 多节点测试。验证记录写明使用的 Docker 服务、镜像/版本、端口、故障注入方式、启动状态和清理状态；进程内模拟只能作为补充，不能替代该证据。

## 7. 量化目标和测量规则

阶段 0 必须为以下指标填写数值和单位，后续阶段沿用同一套测试数据和环境：

- 最大记录、事务、批次、日志段和快照大小。
- 单节点平均/峰值写入量，以及同步中心合计峰值写入量。
- 本地提交 p50/p95 延迟和最大恢复时间。
- 最旧未同步事件年龄、同步滞后和重试次数上限。
- 待发送/待接收/待应用队列容量和磁盘占用阈值。
- 高优先级事件的最大等待时间，以及热点分区对其他分区的延迟影响上限。

测量结果必须包含硬件或容器资源、数据规模、运行时长、预热方式、采样方法和版本号。只有编译通过或单次手工运行，不能作为性能达标证据。

## 8. 停止规则和下一步

遇到以下情况时停止推进当前阶段，并登记阻塞项：

- 文件格式、提交确认或游标规则仍有两种可解释行为。
- 失败结果只能靠日志猜测，无法通过状态、错误码或指标核验。
- 集成测试依赖远程集群、真实生产服务或未记录版本的环境。
- 当前切片的测试失败，或修复引入了其他切片的未验证改动。
- 量化阈值尚未冻结，却需要宣称吞吐、容量或弱网性能达标。

当前计划文档完成后，下一份设计交付应是 Slice 0A 的协议字段、状态机和故障矩阵；完成并验证 Slice 0B 后，才进入日志记录帧实现。完整 SQL、自动分片、跨节点事务和自动冲突合并继续保持在需求基线规定的首期范围之外。

阶段 0 的机器可读冻结规范、故障矩阵和验收入口见[阶段 0 验收说明](stage-0/acceptance-v0.1.md)。

个人可用版的逐工作日日程见[个人可用版每日开发计划](daily-development-plan-v0.1.md)。该日计划把阶段 0–3C 编排为 100 个工作日；阶段 4–6C 需要在个人版验收数据基础上重新估算。
